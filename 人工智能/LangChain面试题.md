### 2. Langgraph 这块state 实现的短期长期记忆怎么做的？

- 当我们使用Langgraph来定义一个graph图的时候，首先需要先定一个状态state。这个state包含了graph的所    有的schema 以及reducer函数，定一个state状态我们通常继承一个父类叫Messagestate，因为父类中已经帮我们定义好了一个messages的key 。这样的话在状态中就包含了一个默认的消息列表。

- 在Langgraph中，不管是长期记忆还是短期记忆，都是围绕着这个状态state的。这些记忆主要是存储state中的历史的交互数据。让大模型从反馈中学习，并且适应用户的偏好。提高大模型生成答案和意图识别的准确率。

- 其中短期记忆是存储单个会话中的交互数据，我们通过设置一个checkpointer，如果短期记忆只是存储在内存中，可以采用InMemorySaver作为checkpointer。是在我之前做的项目中，我们还要保证短期记忆的数据持久化，所以我们采用的是PostgresSaver。但是在每次调用智能体或者执行graph的时候，都必须要传一个thread_id。在一次会话中，随着交付的轮次越来越多。短期记忆中的交互数据很有可能会超出上下文长度。所以在我们之前的项目中，我还做了短期记忆的摘要处理。据我所知，在LongGraph1.0之后，还可以通过中间件，专门负责短期记忆的摘要处理。

- LongGraph的长期记忆是保存所有会话的交付数据。并且一般都会直接持久化到关系型数据库中或者向量数据库中。一般需要设置一个store。我在之前的项目中用过PostgresStore。但是往往需要自己手动调用put函数把数据持久化到数据库中。可以根据需要，把长期记忆数据通过嵌入模型向量化，然后再保存到知识库中。这样就可以实现长期记忆存储的语义检索。

### 3. Langgraph 这块有没有做humen in th loop？

- 在 LangGraph 中，Human-in-the-loop（HITL，人机协同）的目的是，对于关键节点引入人类监督和干预，
  从而在保持效率的同时，显著提升系统的可靠性、安全性与合规性。

- LangGraph 主要通过 中断机制、状态管理 和 恢复命令 三者协同来实现Human-in-the-1oop。

  - 1、中断（Interrupt）：这是触发人工干预的起点。在定义的工作流节点中，可以调用 interrupt（）函数。一旦执行到此，整个图的工作流会立即暂停，并将预设的信息（如需要审核的内容、待决策的问题）返回给调用方。同时，LangGraph会抛出一个特殊的 GraphInterrupt异常。

  - 2、检查点与状态管理（Checkpointer）：为了实现“断点续跑”，LangGraph 依赖 检查点（Checkpoint）机制。因为，一个checkpointer会在每个节点执行完毕后，将当前的完整状态（State）持久化保存下来。当工作流在某个节点中断时，其状态已被妥善保存，确保人类干预后能够从精确的位置恢复执行。

  - 3、恢复（Resume）：当人类做出决策（如“批准”或“拒绝”又或者输入新的其他信息）后，需要通过 Command原语 来恢复工作流。LangGraph会根据 thread_id找到对应的检查点，然后从触发中断的那个节点的开头重新执行该节点的函数。当重新执行的代码再次运行到 interrupt（）语句时，这次它不会真正中断，而是直接将Command （resume=...）中提供的值作为“返回值”注入，然后节点函数继续执行后续逻辑

### 4. Langgraph 每次的回答时间大概多久？

每次回答的时间大概在1~5秒之间。为了让用户体验更好，我们全程采用了流式输出，而且当执行到某一个中间节点时，也会把这个中间节点执行的结果，通过流式输出的方式展示在前端界面上。

### 5. Langgraph 与 Langchain 区别

#### 5.1 LangChain是智能体开发和RAG开发的核心基础框架，尤其从0.3版本之后。更适合：

- 快速开发简单应用（如单轮问答、文档摘要、基础 RAG）。
- 集成外部工具（如调用国内外各种AI大模型的 API、数据库查询），且流程固定（无需动态循环）。
- 利用现有模板（如 create_sql_query_chain 生成 SQL、create_retrieval_chain 构建 RAG）快速落地。
- 用它的create_agent函数（老版本是create_react_agent）能让你用极少的代码搭建一个功能完善的智能体，快速验证需求。虽然它底层也是依赖langgraph提供graph的实现。

#### 5.2 LangGraph 提供的底层控制能力是构建可靠复杂系统的关键框架，更适合：

- 复杂多步骤任务，细粒度控制流，原生支持条件分支、循环、重试、中断等复杂逻辑。
- 有状态的多轮交互（如客服对话机器人，需记忆历史对话并动态调整策略）。
- 多 Agent 协作（如“产品经理一设计师一工程师”的任务分工流程）。
- 项目开发控制力强、可靠性高，适合生产级的长周期、高稳定性要求的应用

### 5.3 function calling 要满足哪些点才能保证模型能较准确的去调用它？

- 明确功能描述：用简洁语言说明函数“能解决什么问题”，避免模糊表述（如“查询天气”而非“处理气象相关”）；
- 规范参数设计：
  - 明确参数类型（字符串 / 数字 /布尔值 / 列表）、必填 / 可选属性（标注required：true/false）；
  - 补充参数约束（如“城市名需为国内地级市”“日期格式为 YYYY-MM-DD”）；
  - 避免过多参数（建议≤5 个），复杂场景拆分为多个函数；
  - 提供格式范例：给出完整的函数调用 JSON 示例, 如`｛"name"："get_weather"， "parameters"：｛"city"："北京"，"date"："2025-11-12"｝｝`，降低模型格式错误概率；
  - 标注返回格式：说明函数返回的数据结构（如“返回｛温度：20°C，天气：晴｝”），方便模型后续处理结果。

### 6. Langchain里面的state状态是什么用途

- 在 LangChain 中，state（状态）是用于在对话或流程的不同步骤之间存储和传递信息的机制，其核心用途是维持上下文连贯性、跟踪流程进度或保存中间结果，确保复杂交互（如多轮对话、工具调用、链式流程）能有序进行。
- 具体来说，state 的主要用途包括：保存对话历史在多轮对话场景中，state 用于存储用户与 AI 的过往交互内容（如用户提问、AI 回答）。这样，后续的模型调用可以基于完整的对话历史生成回应，避免“失忆”，让对话更自然连贯。
- 跟踪流程状态在复杂的链式流程（如SequentialChain）或工具调用（如Agent）中，state 用于记录当前流程的进度、已完成的步骤或需要传递给下一环的关键信息。例如：Agent 在调用工具后，会将工具返回的结果存入 state，供下一次决策时参考。
- 传递上下文数据当多个节点或者多Agent协同工作时，state 可以作为数据传递的“载体”，将前一个组件的输出（如解析后的用户意图、提取的实体）传递给下一个节点，确保信息不丢失
- 支持动态逻辑控制基于 state中存储的信息（如用户选择、流程阶段标记），可以动态调整后续的执行逻辑（如分支选择、工具调用策略），实现更灵活的交互流程。例如：根据 state 中记录的用户“是否已提供必要信息”，决定是继续追问还是直接生成结果。

### 7. Langgraph 是怎么实现不同用户的历史信息区分？

 在 LangGraph 中，区分不同用户的历史信息主要通过会话（Session）隔离和状态（State）管理机制实现，核心思路是为每个用户或会话分配独立的状态存储空间，确保不同用户的历史数据互不干扰。具体实现方式如下：

#### 7.1 基于Thread_id的隔离

LangGraph 通过Thread_id 作为区分不同用户或会话的唯一标识，类似web 开发中的“会话标识”。每个用户的交互会被绑定到一个独立的Thread_jd（通常由前端传入Thread_id或者开发者在初始化会话时指定，如用户 ID、随机生成的 UUID 等）。在调用LangGraph 的run或stream方法时，需传入当前用户的Thread_jd，框架会根据该 ID 定位到对应的状态存储区域。

#### 7.2 状态存储（Checkpointer）的分层设计

LangGraph 的状态存储依赖于Checkpointer（检查点）组件，其核心功能是持久化和恢复每个会话的状态（包括对话历史、流程进度等）。Checkpointer 会按照Thread_id对状态进行分层存储，确保不同会话的状态相互独立。
内置 Checkpointer：如MemorySaver（内存存储，适合测试）、SqliteSaver（本地数据库存储）等，均默认以session_id作为键（Key）区分不同用户的状态。
自定义 Checkpointer：若需对接外部存储（如 Redis、MySQL），开发者只需实现Checkpoint接口，确保存储逻辑中以Thread_id作为唯一索引即可。

#### 7.3 状态（State）对象的会话绑定

LangGraph 中的State对象（定义对话状态的结构，如包含messages字段存储对话历史）是会话级别的，即每个Thread_id对应一个独立的 State 实例：用户交互时，框架会根据Thread_id加载该用户的 State（若不存在则初始化），并在交互结束后将更新后的State（如新增的对话内容）通过 Checkpointer 保存。

### 8. 框架是LangGraph，Agent 之间交互的协议是什么

在 LangGraph 框架中，Agent 之间的交互并不依赖外部通信协议（如 HTTP、gRPC 或 MCP），而是通过 框架内部的状态驱动消息传递机制 实现的，简称handoff。其“协议”本质是 基于共享状态（State）的结构化消息流转。

每个智能体都是图中的一个独立节点。交接通过图的边来控制。具体又可分为两种方法：

- 1、条件边：在某个节点（如监督者智能体）执行完毕后，由一个条件函数根据当前状态决定下一个要执行的节点。 这种方式类似于传统的流程图，路由逻辑是预定义且相对静态的。
- 2、Command 对象：节点在执行后可以直接返回一个 Command对象，该对象既能更新全局状态，又能通过 goto 参数显式指定下一个要执行的节点。这种方式将路由逻辑放在节点内部，更加动态和灵活。所以第二种方式更加通用，在我之前的Multi_agent项目中，由于我采用的是langgraph==0.6，和langgraph-supervisor库，所 以，我来用Python的闭包，动态的为每个agent之间都创建一个handoff工具，handoff工具中通过返回Command对象，把需要交接的上下文数据封装到一个TooLMessage中，传递给下一个Agent。当需要进行Agent的 交接时，LLM基于上下文和用户输入的指令，来动态意图识别决策调用某个handoff工具，最终完成交接过程。

### 9. Langchain中user字段和system字段有什么区别

- System 字段：模型的“行为手册”，构建一个系统提示词消息（SystemMessage）

  - 本质：对模型的全局约束，贯穿整个对话生命周期，优先级高于单次 user输入。
  - 内容特征：通常是指令式、规则式的文本，而非具体问题。
  - 典型场景：
    - 定义角色：“你是一名专业的Python开发工程师，回答问题时必须给出可运行的代码示例"；
    - 约束格式： "所有输出结果必须以JSON格式返回，包含'步骤'和'结果'两个字段"；
    - 补充背景：“以下对话中提到的'项目A'是指2025年上线的电商数据分析系统"；
    - 限制范围："仅回答与LangChain相关的问题，其他问题请告知用户无法解答"。

- User 字段：模型的“待办任务”，构建一个用户指令消息（HumanMessage）

  - 本质：用户的具体交互输入，是模型需要直接响应的内容，每次 user 输入通常对应一次模型输出。
  - 内容特征：以问题、指令、对话内容为主，是具体的任务诉求。
  - 典型场景：
    - 提问：“如何用LangChain实现工具调用？"；
    - 下达任务：“解析这份文本中的用户订单信息，提取订单号和金额"；
    - 多轮对话：“刚才的代码示例有bug，帮我修复一下"。

| 属性         | System 字段                                | User 字段                              |
| ------------ | ------------------------------------------ | -------------------------------------- |
| 优先级       | 高（全局约束，覆盖单次用户输入的隐含规则） | 低（服从 system 规则，是具体执行内容） |
| 生命周期     | 通常贯穿整个对话会话（多轮复用）           | 单次/多轮交互，随对话动态变化          |
| 内容属性     | 规则、背景、角色定义（静态/半静态）        | 问题、任务、对话内容（动态）           |
| 模型响应方式 | 不直接响应，而是约束响应的逻辑/格式        | 直接响应，是模型输出的核心依据         |
| 缺失影响     | 模型行为无约束，可能偏离预期（如答非所问） | 无具体任务，模型无法生成有效输出       |

### 10. state类中定义了哪些信息，state类的继承类是什么

在LangGraph中，State本身并不是一个具体的类，而是一个类型约定。它定义了贯穿整个工作流执行过程的共享数据的结构类型和reducer函数。其中Reducer函数可以理解为：节点更新如何应用于 State 的关键。State 中的每个键都有其自己的独立 reducer 函数。如果未明确指定 reducer 函数，则假定对该键的所有更新都是直接覆盖它。

State一般可以继承三种父类：

- 1、TypedDict（来自Python typing模块）：这是最轻量级的选择，主要在编码时提供类型提示，但是，不会在运行时进行数据验证。
- 2、Pydantic 的 BaseModel： 这是功能最强大的选择。它会在运行时强制进行数据验证，并支持设置默认值、字段约束（如数值范围）、自定义验证器等，非常适合构建健壮的复杂应用。
- 3、有langgraph框架提供的父类MessagesState，它本质也是继承了TypedDict，好处是可以继承父类定义messages这个key以及对应的reducer函数实现消息列表的自动追加。

一般，我在项目中采用第三种。

```python
from typing import TypedDict, List
class MyState(TypedDict):
    messages: List[str]
    current_intent: str
    
from pydantic import BaseModel, Field
class MyState(BaseModel):
    messages: List[str] = Field(default_factory=list)
    score: int = Field(ge=0, le=100)  # 值必须在0到100之间
    
    
class MyState(MessagesState):
    # 自己 定义其他key
    pass
```

### 11. Fuction call 在大语言模型中如何使用的，从原理上解释下​

我理解的Function Calling（函数调用）Function Calling 是基础协议：

- 它是由OpenAI、Anthropic、智谱AI等模型提供商在其API层面实现的标准化功能。它规定了模型如何接收工具描述以及如何返回结构化调用请求。
- 它的本质是让LLM扮演一个“决策大脑”的角色，而实际的工具执行则由外部代码环境完成。其工作流程遵循一个清晰的“思考-行动-观察”循环。`模型本身不执行代码，它只负责理解意图和生成结构化的调用指令`。实际执行发生在我们自己的代码环境中，这既保障了安全，也使得模型能够处理它本无法完成的任务（如实时数据查询、复杂计算等）。

在LangChain中开发的Agent调用工具，其底层机制就是Function Calling。LangChain在底层模型协议之上，构建了一层抽象和封装，提供了一套统一、便捷的接口来使用这些功能。工具（Tools） 就是封装好的Function。Agent 利用LLM的Function Calling能力，自动管理了所示的“思考-行动-观察”循环。它会自动判断何时调用工具、调用哪个工具，并自动将工具结果反馈给模型，直到得出最终答案.
